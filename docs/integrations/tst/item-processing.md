# 自定义物品处理的公共入口

`ItemProcessingRecipes` 按原生 `RecipeMap` 对象注册 `ItemProcessingRecipeSource`，不按控制器类名分发。GT 最外层 `checkRecipe()` 在原有 `startRecipeProcessing()`／`endRecipeProcessing()` 事务范围内调用公共处理器；未注册来源或未安装无限能源仓时继续调用机器原生 `checkProcessing()`。

来源提供每个输入物品的精确产出倍率、整轮耗电、运行时间及未匹配物品是否返还；`validate(machine)` 在任何资源提交前检查研究、模式等启动条件。任意使用同一 RecipeMap 的控制器共享来源；其他模组可以注册自己的来源，不需要新增单机执行 Mixin。来源必须确认这个 RecipeMap 的所有使用者共享同一转换语义；启动条件必须放入来源校验；需要消耗额外启动资源或多种原料联合匹配的处理器，不能直接套用单物品转换来源。

公共执行层复用 `BigRecipeInventory` 的精确库存和扣料事务，混合输入共用一个并行上限、无线余额与完整输出容量预检。样板缓冲区保持隔离，镜像只提交一次。所有金额使用 `BigInteger`；运行期间沿用 `WirelessRecipeState`、公共逐 tick 扣电、暂停恢复、输出队列及 NBT。余额不足和输出容量预检失败不会提前扣料。免费的无限输入必须有有限手动上限。

TST 只注册 `OreProcessingVisualRecipeMap` 的数据来源：每次查询实际 `OP_Logic`，读取精确产出因子，不创建第二份 RecipeMap，不缓存注册表的数量。非矿石输入按原有规则返还；润滑油的周期消耗继续由控制器自己的 `onRunningTick()` 执行。普通能源仓保留来源时长；终极能源仓沿用玩家指定时长，总耗电保持精确。

Waila 判断注册来源和运行能力，公共代码不识别矿处类名。任意自定义机器仍保留它自己的运行回调，不能仅凭继承公共基类推断任意算法都符合此接口。

验证包括纯计划的混合配方、共享电量和手动上限、累计输出容量、超过 long 的数量、免费返还与无限输入边界；运行时自检通过真实 GT 配方调用入口，验证 TST 矿处和另一种来源、多个控制器、非矿石返还、输出拒绝、润滑油周期、暂停和 NBT 恢复、启动条件拒绝与原生回退、运行时替换／删除配方及大于 int 的产出倍率。
